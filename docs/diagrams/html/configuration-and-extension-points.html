4. Configuration map
設定是控制面，不是 pipeline 本身

這一頁把 schedule、models、route wiring 與 engine override 分層表示。 重點是讓人看懂：有些設定只是選資料，有些設定會真的替換 runtime 的實作。

使用端專案
場域專屬資源與實作

這一欄是使用端專案真正要維護的東西。它們不是 runtime 的共用骨架，而是各場域自己的變體。

schedule.jsonphase selection
決定哪個 phase 走哪種行為，常被 ScheduledInferenceEngine 使用。
configs/models.yamlmodel config
對應使用端專案的模型設定與參數，供 custom model classes 讀取。
自訂模型類replaceable
自訂 inference、publish 與 streaming engine 都屬於這一側的擴充。
configuration
把 backend 與 engine 接線起來

中間這層是控制面。它的工作不是直接跑 pipeline，而是決定 runtime 要怎麼接 backend、 要不要替換 engine、以及 subscriber 要掛哪些 inbound routes。

shared inbound backend
共用的 backend 連線底座，交給 MessagingClientProvider。
route config
phase / matching / events routes 由這裡決定要不要訂閱。
engine overrides
指定哪個 task 要換成自訂 inference / publish / streaming engine。
runtime effect
設定不是資料本身，而是驅動 runtime 行為的指令集合。
control plane chooses wiring
edge_core runtime
真的被 wire 起來的元件

右欄顯示控制面最後落地到哪些 runtime component。這裡的重點是看出「設定對應到哪個 hook」。

MessagingClientProviderbackend
承接 shared inbound backend，讓 subscriber 與 runtime 有共同的訊息來源。
start_messaging_subscriberroutes
讀 route config，決定要掛哪些 phase / matching / events updates。
InferenceTask / StreamingTask / PublishResultTaskoverridable
engine overrides 會在這些 task 上生效，替換掉預設行為。
TaskContextshared state
subscriber 與 runtime 會把狀態寫進來，讓 stage 之間共享。
Quick read
這張圖的重點

schedule.json 決定 phase

它更像開關與策略表，不是 pipeline 的實際運算。

route config 決定 inbound wiring

phase / matching / events 的訂閱都要先由控制面開好，runtime 才能接到資料。

engine overrides 真的會換實作

這是最重要的 extension point，因為它會直接改變 inference / publish / streaming 的行為。
