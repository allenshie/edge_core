Runtime Bootstrap and Shutdown

這張圖不是在畫「有哪些元件」，而是在畫「啟動時誰先做什麼、關閉時誰先收什麼」。 它把 launcher、edge.main、subscriber、health server 與 workflow runner 串成一條可讀的時間線。

2. Runtime sequence
啟動鏈路要先把依賴接好，再跑 workflow

左邊先把「這個 runtime 要記住什麼」講清楚，右邊用四段時間線把啟動、訂閱、執行與關閉分開。 這樣比較容易看出 health server 是可選分支，而不是每次都一定存在。

boot contract

讀這張圖的方式

  • Launcher 只是進入點，真正的 runtime 在 edge.main。
  • Messaging client 與 subscriber 先建立，才能接 backend 的 inbound routes。
  • Health server 不是每次都啟動；它是否存在，會影響 runner 的型別選擇。
  • Workflow runner 負責 startup task 與 scheduler loop，最後把收尾流程走完。
這張頁面故意比 Mermaid 寬鬆一點，因為啟動鏈路的重點是順序與責任，不是符號本身。

Boot

launch entry
User → Launcher
start service
外部執行環境把服務拉起來，進入 edge_core 的啟動入口。
main.py call main()

launcher 只是包裝層，真正的啟動流程從 edge.main 開始。

Launcher → edge.main
enter runtime
把控制權移交給共通 runtime，後面才開始建立 messaging 與 workflow。
edge.main bootstrap

這一步把 site-specific 入口和共通 runtime 的責任切開。

Wire services

runtime wiring
edge.main → MessagingClient
build client
先建立 messaging client，後面 subscriber 與 route wiring 才有地方掛。
messaging client ready

這是 runtime 的外部連線底座，不先做這一步，後面的 inbound routes 沒辦法生效。

edge.main → StartSubscriber
scan enabled inbound routes
只訂閱真的有開的 route，避免把不需要的 backend 邏輯掛進來。
start_messaging_subscriber route scan

這一段把 App Backend 的 updates 接到 runtime 狀態，包含 phase 與 matching 相關路由。

Run

execute workflow
edge.main → HealthServer
start health server
如果健康檢查開啟，就先把 HTTP probes 起來；沒有開就回傳空值。
optional healthz / readyz

這是可選分支，不是 runtime 必需。頁面上把它獨立出來，避免誤解成固定步驟。

edge.main → WorkflowRunner
build runner
根據 health server 是否存在，選擇對應的 runner 類型。
runner startup + loop

runner 會先跑 startup task，再進入 scheduler loop，這是 runtime 真正在做事的地方。

Stop

shutdown path
WorkflowRunner → edge.main
stop runner
scheduler loop 結束後，runner 把控制權交回 runtime 進行收尾。
shutdown stop signal

這一段對應的是優雅退出，不是強制中斷。

edge.main → Client / HealthServer
close outbound resources
最後關掉 messaging client 與 health server，避免留下殘留連線。
cleanup close / stop

收尾順序跟啟動順序相反，這樣比較容易維持資源整潔。
